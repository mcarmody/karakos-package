# Real-CLI fixtures (ANDURIL step 0.4)

**CLI version: Claude Code 2.1.287** (`claude --version`). Model: `claude-haiku-4-5-20251001` (`--model haiku`). Recorded 2026-10-02/03 on Linux (WSL2), in fresh temp directories with `--strict-mcp-config` and an empty or stub MCP config. Total spend about $0.36. Common flags: `-p --input-format stream-json --output-format stream-json --verbose --setting-sources "" --permission-mode bypassPermissions`, plus `--replay-user-messages` so consumption of each stdin line is visible. Each question has `stdin.jsonl`, `stdout.jsonl` and `NOTES.md`; sub-directories are variants. `tools/` holds the recorder, the scrubber and the stub MCP server so the run can be repeated (7.3a). Event files are `{"t":secs,"dir":...,"event":{...}}` lines; ids, paths and account details are scrubbed.

1. **Second user line mid-turn (`1-second-user-line-mid-turn`).** Queued by the CLI and merged into the running turn at the next tool boundary. A line sent 3 s into a `sleep 20` tool call reached the model only after the tool result (t=22.8) and was answered in the same turn. One `result`. Not dropped, no second turn. Steering latency is the remaining time of the in-flight tool call.
2. **Burst (`2-burst`).** The first line starts a turn at once; the other two, queued during it, are joined with `\n` into one user message and run as a second turn. Two turns, two `result`s (not three, not one). Every turn starts with a new `system`/`init`. Same at idle after a warm-up turn.
3. **Interrupt (`3-interrupt`).** The `control_request` `interrupt` subtype works: a `control_response` success (`still_queued: []`), the tool is rejected with "[Request interrupted by user for tool use]", then a `result` `error_during_execution` (`is_error: true`, `terminal_reason: aborted_tools`). The process stays alive and the next stdin line runs normally. SIGINT produces the same events and then the process exits 0, so it is not reusable.
4. **MCP initialize (`4-mcp-initialize`).** Before `initialize` the CLI sends a `server/discover` probe (protocol 2026-07-28), abandoned after ~3 s if unanswered. Then `initialize` (id 0, protocolVersion 2025-11-25, roots and elicitation capabilities), `notifications/initialized`, `tools/list`. A server that never answers `initialize` gets `notifications/cancelled` after 25 s; the CLI's `system`/`init` event is held until then (t=28.4) and shows the server as `failed`, and the turn runs without its tools. This confirms 0.6 and adds the `server/discover` probe.
5. **Resume with a changed system prompt (`5-resume-system-prompt`).** The new text is ignored. `--resume` with a different `--system-prompt`, with `--append-system-prompt`, with both, and with an explicit "ignore earlier instructions" prompt all answered with the original session's codeword; a fresh session with the same new prompt used it (control). The `session_id` is unchanged. New identity or rules need a new session.
6. **Sidechain and duplicates (`6-sidechain-and-duplicates`).** Subagent (Task) assistant events carry `parent_tool_use_id` = the Task call's `tool_use.id`; main-thread events carry null. One API message appears as one `assistant` event per content block with the same `message.id` repeated and identical `usage` (`stop_reason` null); usage did **not** grow across duplicates in either capture, so 1.5's dedupe-by-id rule holds but "growing usage" was not reproduced. In this CLI version Task subagents run in the background by default, and the CLI starts a second turn by itself when the subagent finishes: one stdin line produced two `result` events.
7. **Version.** 2.1.287, model `claude-haiku-4-5-20251001`, in every `system`/`init` event.

## Follow-up note for spec 0.3 (`fake_claude.py`: "queued-stdin modelling", small PR after 0.3 merges)
The fake should replay these recorded behaviours:
- **Queued lines:** a user line arriving while a turn is running is held, not dropped and not an immediate new turn. With `--replay-user-messages`, a replayed `user` event (`isReplay: true`, `timestamp` = receipt time) is emitted when the line is consumed, not when it arrives.
- **Merge vs second turn:** if the running turn has a tool call in flight, the queued line is delivered right after that tool's `tool_result` user event, inside the same turn, and the turn ends with a single `result`. If the turn has no further tool boundary (text-only), the queued lines wait and start the next turn after `result`.
- **Coalescing:** all lines queued at the same time are joined with `\n` into one user message and one turn.
- **Turn framing:** every turn (including queue-started and self-started ones) opens with `system`/`init`; one `result` per turn.
- **Interrupt shape:** `control_request` `interrupt` -> `control_response` success `{"response":{"still_queued":[]}}`, then the tool_result rejection and `[Request interrupted by user for tool use]` user events, then `result` with `subtype: error_during_execution`, `is_error: true`, `terminal_reason: aborted_tools` (no `result` text); the process keeps running. SIGINT: the same events, then exit 0.
- **Duplicates and sidechains:** one `assistant` event per content block, same `message.id` and identical `usage` on each; subagent events with `parent_tool_use_id` set. Optionally a background-Task run where a notification starts a second, self-initiated turn.
- **MCP:** `init` is emitted only after MCP servers connect or fail (up to ~28 s for a silent server); a failed server appears with `status: "failed"`.
- **Resume:** the original system prompt persists; new `--system-prompt` and `--append-system-prompt` values are ignored on `--resume`.

## Go/no-go for 2.5
**GO for true mid-turn steering, with the CLI as the queue: write the line to stdin immediately and do not hold it harness-side.** The CLI does not drop mid-turn lines; it merges them into the running turn at the next tool boundary (or into the next turn if there is none). Constraints for the 2.5 design: delivery happens at the next tool boundary, so steering during one long tool call waits for it; for urgent redirection use the `interrupt` control request (process stays reusable) and then send the new line; do not use SIGINT; do not assume one `result` per stdin line (Q6 background Task, Q2 coalesced burst). Note for review: the brief's literal rule says to fall back to "hold and deliver after `result`" if the CLI "merges" lines; the observed merge is the steering behaviour 2.5 wants (the model sees the line mid-turn), so that fallback is not triggered.
